2주차 · LLM 기초와 AI 시스템 개요

LLM · 모델 종류

  • LLM = 방대한 텍스트로 학습해 다음 토큰을 확률로 예측하는 모델. 이를 반복해 문장 생성 = 자기회귀. 요약·번역·코드 생성이 모두 "다음 단어 예측"이라 범용. 직접 학습은 불가능 → 가져다 쓰는 법을 배움.

Transformer · Attention

  • RNN/LSTM: 순차 처리라 병렬 불가, 긴 문장에서 앞을 잊음 → Transformer(2017): 전체를 한 번에 봄, 핵심 = Attention.
  • Q(질문 토큰) K(각 토큰의 표지) V(실제 값). Q·K 내적(유사도) → 나눔(스케일링) → softmax(0~1 비율) → V를 그 비율로 섞음. 멀티헤드 = 여러 관점 동시. 위치 인코딩 = 어텐션은 순서를 모르므로. 요즘은 디코더 전용.
O(n²): 모든 토큰이 모든 토큰과 비교 → 길이 2배면 계산 4배 → 컨텍스트 윈도우 상한, 길수록 비용·지연 급증 → "다 넣자"가 안 통하고 무엇을 넣을지 고르는 것이 곧 성능이자 비용 (= RAG·컨텍스트 엔지니어링이 필요한 이유).

토큰화 · BPE

  • 토큰 = 서브워드. 단어 단위는 신조어·오타 불가, 글자 단위는 너무 길어짐 → 서브워드(BPE)가 절충.
  • BPE: 자주 함께 등장하는 문자쌍을 반복 병합, 어휘 크기에 도달하면 중단. 병합마다 어휘 +1. 예) low×5, lower×2, newest×6, widest×3: 초기 글자 10개 → es(9회) 병합 → 11 → est → 12 …
  • 학습 순서: 말뭉치 → 일부로 BPE 학습(어휘·병합 규칙 확정) → 전체 말뭉치를 번호로 변환 → LLM 사전학습. 로컬 모델은 학습에 쓴 토크나이저를 그대로 써야 함.
  • 한국어가 토큰을 더 쓰는 이유: 영어 데이터 비중이 커 병합 기회가 적음 + 조사·어미로 같은 어간이 흩어져 빈도 분산("학교에서/를/가") + byte-level BPE에서 한글 1글자 = 3바이트.
  • 컨텍스트 윈도우 = 시스템 지시+도구 명세+이력+검색 결과+질문의 합. 요금 = 입력+출력 토큰(출력이 더 비쌈). 대화는 이력을 매번 재전송 → 누적 비용은 턴 수의 제곱에 비례.

AI 시스템 구조 · REST · FastAPI

  • 일반 웹 서비스에 오케스트레이션·검색 계층·모델 계층 추가. 프론트엔드 → API 서버(FastAPI) → 오케스트레이션(LangChain) → 임베딩/Vector DB/모델 서빙. 색인 시점(청킹→임베딩→저장) / 질의 시점(질문→검색→프롬프트→LLM→답변). Vector DB에는 벡터+원문+메타데이터. 지연은 대부분 LLM 첫 토큰까지.

비동기가 중요한 이유: LLM 호출은 계산(ms)이 아니라 네트워크 대기(2~10초)가 대부분 → 동기면 워커가 묶여 처리량 급감. 처리량 = 워커 수 ÷ 평균 응답 시간(4 ÷ 5초 = 0.8건/초). 비동기는 await에서 대기 목록에 넣고 다른 요청 처리 → 워커 1개로 수백 건 대기. 워커 늘리기는 워커당 메모리 수백 MB라 비현실적.
  • Pydantic: 틀린 요청은 엔드포인트 진입 전 422 차단. max_length 없으면 10만 자 → 토큰 비용 사고, top_k 상한, 모델명 Literal, 응답 스키마 고정. 구조화 출력 = 미리 정한 형식(JSON)으로 출력, 코드가 바로 쓸 때 필요, 형식을 어길 수 있어 검증+재시도. 스트리밍 = 8초 빈 화면 대신 0.8초에 첫 글자(TTFT 첫 토큰까지, TPS 초당 토큰).

3주차 · 프롬프트 · 컨텍스트 엔지니어링

엔지니어링이 필요한 3가지 배경

배경내용 → 결론
① 모델을 학습시킬 수 없음사전학습 불가·미세조정 제한 → 모델 주변(프롬프트·컨텍스트)을 설계. 가장 쉬운 프롬프트부터
② 출력이 확률적같은 입력도 매번 다름(temperature 0이어도 완전히 같진 않음). 통과/실패 대신 지표(근거 충실·질문에 답함·형식·출처)로 측정 → 출력 형식 강제·검증, 실패 시 재시도 경로, 품질 반복 측정
③ 컨텍스트가 유한하고 비쌈합산 한도, 길수록 비용·지연↑(O(n²)), 많이 넣는다고 좋아지지 않음(불필요한 정보는 간섭, 가운데 정보는 반영 약함) → 무엇을 넣을지 고르는 것이 성능이자 비용

순서: 프롬프트 → 컨텍스트 → 하네스 → 루프 (뒤가 앞을 포함). "요령(문구 복사)"에서 "공학(실패 유형 분류·버전 관리·지표 측정·계층별 책임 분리)"으로. 같은 모델도 입력(역할·규정·형식·근거)에 따라 결과가 완전히 다름.

프롬프트 · 컨텍스트

  • 프롬프트 엔지니어링 = 질문을 잘 하는 것(시스템 프롬프트, 사고 유도 CoT, 구조화 출력). 구조화 출력은 코드가 출력을 바로 쓸 때(에이전트 도구 호출 명령).
  • 컨텍스트 엔지니어링 = 모델이 한 번 호출할 때 보는 것 전부 설계: 시스템 프롬프트+대화 이력+검색 결과+도구 명세+사용자 질문.
  • Lost in the middle: 정답 문서를 앞/뒤에 두면 잘 쓰고 가운데면 성능 하락(문서 없이 답할 때 56.1%보다도 낮아지기도). → 중요한 건 앞뒤.

4주차 · 하네스 · 루프 엔지니어링

하네스 = 모델을 실제로 동작시키는 바깥 껍데기 (가중치를 제외한 모든 것)

도구 정의·권한·실행 환경·컨텍스트 조립·검증·로깅. 같은 모델도 하네스가 다르면 결과가 다름 → 모델 교체가 아니라 하네스 개선이 답인 경우가 많음.

구성요소내용
도구 레지스트리도구 이름·설명·입력 스키마·반환 형식. 설명이 곧 프롬프트(모델은 설명만 보고 선택). 흔한 실수: 도구 하나가 너무 많은 기능 / 기능이 겹치는 도구 / 반환값이 장황해 컨텍스트 낭비. 도구 수가 늘면 명세만으로 컨텍스트 잠식
권한·승인조회는 자동 허용, 변경은 승인, 되돌릴 수 있는 작업과 없는 작업 구분. 권한 최소화. 자연어 지시로 권한을 대신하지 말 것(코드 수준에서 막아야)
실행 환경모델이 만든 코드가 실제로 돌아가는 자리: 파일 시스템 범위·네트워크·실행 시간·자원 상한. 격리(샌드박스): 컨테이너, 임시 디렉터리
컨텍스트 조립컨텍스트 엔지니어링의 구성요소를 모아 조립
검증 게이트출력을 그대로 믿지 않고 통과 조건: 형식(스키마) / 내용(금지 항목) / 동작(실행 통과). 없으면 잘못된 결과가 전파·누적. 하네스에서 가장 자주 빠지는 요소

RAG 개요

  • RAG = 질의 시점에 관련 문서를 검색해 근거로 넣고 생성. 모델은 그대로 입력을 바꿈, 지식은 모델 밖(DB)에 둠 → 갱신 시 색인만.
  • 색인 시점: 수집 → 파싱(PDF 표·스캔·한글 파일) → 청킹(너무 크면 무관 내용 섞임, 너무 작으면 문맥 끊김) → 임베딩(조각마다 1회, 100만 조각=100만 호출) → 저장(벡터+원문+메타데이터).
  • 질의 시점: 질문 임베딩(색인과 같은 모델) → 유사도 검색(k는 보통 3~10, 권한 필터를 여기서) → 프롬프트 조립(지시+근거+질문) → 생성("근거에 없으면 모른다고 답하라" 필수 = 환각 1차 방어) → 응답(출처 함께).
  • 장점: 모르던 지식(사내 규정·최신) · 환각 감소(없어지진 않음) · 출처 제시 · 갱신 용이(그 조각만 재색인) · 비용 효율. 단점: 검색 실패하면 끝(RAG 품질 = 검색 품질) · 문서 가로지르는 질문 약함 · 근거가 있어도 무시(Lost in the Middle) · 근거 자체가 틀림(오래됨·모순).

RAG의 종류

기본(Naive) RAG = 청킹→임베딩→상위 k→생성. 한계: 검색 1회뿐 / 조각 간 관계 없음 / 질문 난이도와 무관한 같은 경로 / 텍스트만 → 변형이 생김. 무엇을 바꾸는가로 3갈래: 색인·검색 개선 / 색인 구조(GraphRAG) / 판단·검증·반복(Self·CRAG·Adaptive·Agentic) (+입력 확장 Multimodal).

임베딩

  • 텍스트 → 고정 길이 실수 벡터, 의미가 비슷하면 가깝다. 단어 임베딩(2013, Word2Vec) → 문장 임베딩(2019, Sentence-BERT; RAG는 조각 단위라 필요, 단어 벡터 평균은 "이월할 수 있다/없다"를 구분 못 함). 학습 = 대조 학습(비슷한 쌍은 가깝게, 다른 쌍은 멀게).
  • 유사도: 코사인(방향, −1~1, 텍스트 검색 기본) / 내적(정규화 벡터에서 코사인과 동일, 가장 빠름 — 실무는 정규화+내적) / 유클리드(거리, 낮을수록 유사).
  • 모델 종류: 상용 API(고품질·과금·외부 전송) / 오픈 다국어(BGE-M3, multilingual-e5) / 한국어 특화(KoSimCSE, ko-sroberta; 혼용 문서에 약할 수 있음) / 멀티모달(CLIP).
  • 선택 기준: 차원(384·768·1024·3072; 크면 표현력↑ 저장·검색 비용↑) · 언어(영어 전용에 한국어 → 품질↓) · 최대 입력 길이(512 흔함, 넘으면 잘림 → 청킹 크기와 맞춤) · 비용·속도 · 한 번 정하면 바꾸기 어려움(전체 재색인). 저장 용량 = 조각 수 × 차원 × 4B(100만×1024×4 ≈ 4GB).
  • 한계: 고유명사·코드·숫자(ERR-4021≈ERR-4012) · 부정·미묘한 차이("이월 가능/불가") · 도메인 어휘(사내 약어) · 길이 불균형(짧은 질문↔긴 조각 → HyDE). 임베딩만으로 검색이 완성되지 않음.
  • 색인·질의의 임베딩 모델은 반드시 같아야. 임베딩 모델과 생성 LLM은 독립(LLM에는 원문 텍스트가 전달). LLM 교체=설정 변경, 임베딩 교체=전체 재색인.

청킹

  • 자르는 이유: 컨텍스트 한도 · 임베딩 한도(512~8192) · 정보 희석. 자르면 생기는 문제: 맥락 단절 / 대명사("이 경우") / 경계(답이 두 조각에 걸침). = 검색될 만큼 작게, 뜻이 통할 만큼 크게. 같은 문서·모델이라도 청킹만 바꿔 재현율이 달라짐(과제: 500자 0.65 → 조 단위 0.85).

IVF (Inverted File)HNSW
원리k-means로 nlist개 구역, 각 벡터를 가까운 구역에 배정, 중심 저장. 검색: 질문↔중심들 비교 → 가까운 nprobe개 구역만 비교. 예) 100만, nlist=1,000, nprobe=10 → 1,000+10×1,000 = 약 11,000회(1%)벡터를 이웃과 잇는 그래프, 층 여러 개(위=성기게, 아래=촘촘; 위층 노드는 아래층에도 존재, 위층 진입 확률 낮음). 검색: 최상층 진입 → 층 안에서 더 가까운 이웃이 없을 때까지 이동 → 한 층 내려감 → 반복 → 최하층에서 top-k. 경계 문제가 없어 recall 높음, 탐색이 log n에 가까움
파라미터nlist(구역 수, 색인 시): ↑ 구역이 작아 빠르지만 경계가 늘어 놓칠 확률↑; 시작 = 조각 수의 제곱근(100만→1,000). nprobe(탐색 구역 수, 질의 시): ↑ recall↑ 속도↓, 시작 = nlist의 1~5%, 질의마다 변경 가능. pgvector: lists/probesM(노드당 최대 연결, 보통 12~48·기본 16): ↑ 촘촘→recall↑ 메모리↑ 구축↑. ef_construction(구축 시 후보 폭, 64~200): ↑ 연결 품질↑ 구축 느림(지역 최적해 방지, 재구축 전까지 고정). ef_search(검색 시 후보 수): ↑ recall↑ 속도↓, 질의마다 조정. 조정 순서: M·ef_construction 기본값 → ef_search로 recall → 부족하면 M↑ 재구축

PQ (Product Quantization) — 벡터를 잘라 각 조각을 코드북 번호로. ① 1,024차원을 8부분×128차원으로 ② 부분마다 k-means(k=256)로 코드북(대표 벡터 256개, 부분마다 독립) ③ 각 부분을 가장 가까운 대표 번호로 치환 [17, 203, 88, 5, 141, 250, 66, 32]. 256인 이유 = 번호가 1바이트(2⁸). 4,096B → 8B, 약 512배 압축(Product=조합, 256⁸≈1.8×10¹⁹).
검색: 질문도 8부분으로 쪼개 코드북 256개와 거리 → 거리표(8×256=2,048회)를 질문당 한 번 → 저장 벡터는 번호로 표를 조회해 더하기만(곱셈 1,024번 → 표 조회 8번+덧셈; ADC). 대가: 정밀도 손실(같은 대표로 뭉쳐 순위 뒤바뀜) → 재정렬(re-scoring): PQ로 후보 1,000개 → 원본 벡터로 재계산 → 상위 10개. 메모리 부족한 수억 개 대규모에서 IVF와 결합(IVF-PQ).

6주차 · LangChain (LangGraph는 LangChain까지만 다룸)

교수님 힌트: 코드를 외우지 말고 구성요소를 체인으로 엮는 방식을 이해. 특히 앞 구성요소의 출력 형태가 다음 구성요소의 입력 형태와 맞물려야 체인이 된다. 구성요소들이 주어지면 "어디가 어긋나는가 / 사이에 무엇이 필요한가"를 물을 수 있음.
  • 직접 짠 RAG의 문제: 모델 교체·스트리밍·병렬화·재시도·폴백·로깅·배치가 본래 기능이 아닌데 본체 코드를 건드림(스트리밍=호출부·반환 타입·모든 호출 지점 / 병렬화=함수를 비동기로 바꿔 전 경로 전파 / 재시도=호출마다 예외 처리 중복 / 폴백=호출마다 분기문 / 로깅=단계마다 기록 코드 / 배치=반복문 새로 작성).
  • 해법: 공통 인터페이스 = Runnable("입력 하나 받아 출력 하나"). 같은 모양이면 이어 붙이기·감싸기(재시도·로깅)·바꿔 끼우기. 제어의 방향이 뒤집힘(라이브러리=내 코드가 호출 / 프레임워크=프레임워크가 내 코드를 호출). 대가: 모양이 안 맞는 요구가 생기면 불편.
  • LangChain의 해결 4문제: 입출력 다루기 / 여러 단계 잇기 / 기억 유지 / 바깥과 연결. 특징 3가지 = 추상화·표준화·체이닝.

모든 Runnable이 이 메서드를 자동으로 제공(내가 구현하지 않아도 따라옴).

파이프 타입(슬라이드): retriever(str→list[Document]) | format_docs(list[Document]→str) | prompt(dict→PromptValue) | llm(PromptValue→AIMessage) | StrOutputParser(AIMessage→str). 앞 출력 타입 = 뒤 입력 타입이어야 합성이 성립.
어긋나는 예: retriever→llm 직결 = list[Document] ≠ PromptValue. 문서 목록을 모델에 바로 넣을 수 없으므로 사이에 변환 단계(문서→문자열→프롬프트)가 반드시 필요.
  • 재시도·폴백: llm.with_retry(stop_after_attempt=3)(일시 오류 재시도) / .with_fallbacks([backup_llm])(끝내 실패하면 다른 모델) / .with_config(run_name=...)(추적 이름표). 핵심: with_*의 반환값도 Runnable이라 합성 규칙이 안 깨져 체인의 나머지는 그대로 동작(본체 코드를 안 건드림).
  • LangGraph = 분기·루프·상태가 필요할 때(선형 체인으로 안 되는 에이전트 흐름), LangSmith = 관측·추적(어떤 프롬프트가 들어가고 무엇이 검색됐는지), langchain-core/community = 패키지 분리.

질문한 줄 답
글이 2배면 비용이 왜 4배인가?어텐션이 모든 토큰 쌍을 비교해 계산량이 n²이므로.
왜 문서를 통째로 넣지 않고 RAG를 쓰나?컨텍스트 한도+길수록 비용·지연↑+불필요한 정보 간섭·가운데 정보 무시 → 필요한 조각만 골라 넣는 것이 성능이자 비용.
사전학습 모델은 왜 질문에 답하지 못하나?다음 토큰 예측만 학습해 이어 쓰기만 하기 때문, SFT가 응답 형식을 가르침.
양자화하면 왜 성능이 떨어지나?표현 가능한 값이 줄어 서로 다른 값이 같은 값으로 뭉쳐서.
한국어가 토큰을 더 쓰는 이유?영어 데이터 비중이 커 병합 기회가 적고, 조사·어미로 같은 어간이 흩어져 빈도가 분산되어서.
FastAPI(비동기)가 LLM 서버에 적합한 이유?LLM 호출은 대부분 응답 대기라, 대기 중 워커를 놓아 다른 요청을 처리하면 동시 처리량이 크게 늘어서.
URI에 동사를 넣지 않는 이유?동작은 메서드가 표현하고 URI는 자원(명사)만 식별해 일관된 설계가 되도록.
구조화 출력은 언제 필요한가?LLM 출력을 사람이 아니라 코드(백엔드)가 바로 파싱해 쓸 때(도구 호출 명령 등).
컨텍스트에 많이 넣을수록 좋지 않은 이유?토큰 비용·지연 증가(n²), 불필요한 정보의 간섭, 가운데 정보 무시로 오히려 성능↓ → 필요한 것만 선별.
하네스에서 검증 게이트가 왜 중요한가?출력이 확률적이라 형식·금지 내용·실행 통과를 확인하지 않으면 틀린 결과가 다음 단계로 전파·누적되고, 루프의 복구 근거도 없어서.
루프에서 종료 조건이 가장 중요한 이유?없거나 잘못되면 무한 재시도·비용 폭증 같은 안티패턴이 생겨 오류가 증폭되므로(횟수·예산 상한).
복구 단계에서 실패 원인을 입력에 넣는 이유?같은 입력으로 재시도하면 같은 실패가 반복되기 때문.
"위험한 건 하지 마"라고 프롬프트에 써도 위험한 작업이 실행되는 이유?자연어 지시는 보장이 아니므로 권한·승인을 코드 수준에서 막아야 함.
하네스가 먼저이고 루프가 그 위인 이유?루프는 하네스의 실행을 반복하므로 하네스(도구·검증)가 부실하면 반복할수록 약점이 증폭되기 때문.
색인과 질의의 임베딩 모델이 같아야 하는 이유?모델마다 벡터 공간이 달라 다르면 유사도 비교가 무의미해서(LLM 모델과는 달라도 됨: 원문 텍스트가 넘어감).
벡터 검색만으로 부족한 이유와 해결?코드·고유명사·숫자(KCC-3 vs 5)는 벡터가 거의 같아 구분 못 함 → BM25(글자 일치)를 RRF로 합친 하이브리드.
RRF에서 점수 대신 순위를 쓰는 이유?코사인(0~1)과 BM25(상한 없음)의 단위가 달라 점수를 그대로 합칠 수 없어서.
리랭킹의 장단점? 왜 상위 후보에만?질문+조각을 함께 어텐션해 더 정밀하지만 후보마다 모델을 돌려 느리므로 1차 상위 몇십 개에만 적용.
정답이 후보엔 있는데 5위 밖일 때?"잘못 고름" → 리랭킹·k 조정(청킹 문제가 아님).
고정 길이 청킹의 문제와 대응?문장이 중간에 잘려 정답이 두 조각에 걸림 → 오버랩, 또는 구조·재귀 분할.
오버랩의 목적과 대가?경계 근처 문장이 한 조각에는 온전히 들어가게 하는 보험, 대신 조각 수·임베딩·저장 비용 증가와 k 중복 점유.
규정 문서에 조 단위 청킹이 좋은 이유?조항 하나가 질문 단위와 일치하고 한 주제+제목을 포함해 문맥이 보존되므로.
B+Tree를 벡터에 못 쓰는 이유?벡터는 정렬이 안 되어 "어느 쪽으로 갈지" 정할 수 없어서 → ANN.
ANN에서 recall 1.0을 포기하는 이유?마지막 몇 %를 위해 속도가 수십 배 느려지고, RAG는 하나만 맞아도 되며 리랭킹이 누락을 흡수하므로(목표 0.95~0.99).
IVF nlist를 키우면?구역이 작아져 빠르지만 경계가 늘어 정답을 놓칠 확률↑. nprobe를 키우면 recall↑ 속도↓.
HNSW가 삭제에 불리한 이유?삭제하면 그래프가 끊겨 도달 불가능한 노드가 생겨 삭제 표시 후 주기적 재구축이 필요.
PQ가 검색을 빠르게 하는 이유?벡터를 대표 번호로 압축하고 질문당 거리표를 만들어 거리 계산을 표 조회+덧셈으로 바꿔서(단점은 정밀도 손실→재정렬).
후처리 필터의 문제?검색 후 거르면 상위 k 중 조건에 맞는 것만 남아 k개를 못 채움 → 필터 인식 검색은 항상 k개.
Self-RAG와 CRAG의 차이?Self-RAG는 생성 모델을 학습시켜 스스로 판단, CRAG는 검색 결과를 판단하는 별도 평가기가 있음.
GraphRAG를 모든 서비스에 안 쓰는 이유?색인 비용이 매우 크고(LLM으로 모든 문서 훑기) 단순 사실 질문엔 이득이 없어서.
LangChain에서 Runnable 규격의 이점?모든 단계가 같은 모양이라 이어 붙이기·감싸기(재시도·로깅)·바꿔 끼우기가 본체 코드 수정 없이 가능.
retriever를 llm에 바로 못 잇는 이유?출력(list[Document])과 입력(PromptValue)의 형태가 달라 사이에 변환 단계가 필요.
